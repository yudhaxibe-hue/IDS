1. 30-SECOND ELEVATOR PITCH (HOW TO INTRODUCE THE PROJECT)
--------------------------------------------------------------------------------
"Our project is an Explainable and Adaptive AI-Based Intrusion Detection System. 
Traditional intrusion detection systems operate as black boxes—they flag an attack 
but cannot explain why, and their accuracy degrades as network traffic patterns 
change over time. 

Our system solves both problems by combining three pillars:
1. Machine Learning Classification (Random Forest on 28 standardized flow features)
2. Explainable AI (SHAP TreeExplainer providing plain-language reasoning)
3. Controlled Concept Drift Adaptation (Kolmogorov-Smirnov statistical tests 
   with an audited, rollback-capable candidate model registry).

The entire system runs 100% locally with zero cloud telemetry and zero payload 
storage, protecting enterprise privacy."

2. HOW THE SYSTEM WORKS (BALL-LEVEL / EASY EXPLANATION)
--------------------------------------------------------------------------------
Think of network traffic like cars on a highway:
- A traditional firewall is a security guard checking license plates (IP addresses). 
  If a criminal changes their license plate, they get through.
- Our AI looks at the *driving behavior* (speed, packet timing, direction of traffic). 
  Even if the attacker changes their IP address, their aggressive driving pattern 
  (DoS flood or portscan) is recognized immediately.

The 4-Step Pipeline:
1. INGESTION: Packets are captured live (via Scapy) or simulated (via Offline Replay) 
   and grouped into 5-tuple bidirectional flows (Source IP/Port, Dest IP/Port, Protocol).
2. FEATURE EXTRACTION: Extracts 28 statistical metrics (duration, packet rates, 
   inter-arrival times, TCP flags) matching the academic CIC-IDS benchmark schema.
3. ML DETECTION: A 100-tree Random Forest classifies traffic as Normal vs. 
   DoS/DDoS, Portscan, Brute Force, or Web Attacks with calibrated confidence.
4. EXPLANATION & DRIFT: SHAP computes exact mathematical feature weights (why it 
   was flagged), while a Kolmogorov-Smirnov test monitors if network traffic 
   patterns are shifting over time.

3. WHAT WAS CHANGED FROM THE ORIGINAL WORD SPECIFICATION & WHY
--------------------------------------------------------------------------------
The project strictly followed the primary engineering specification (Milestones 0 to 8). 
However, 5 practical engineering enhancements were made to ensure zero launch failures 
and high academic rigor:

1. Automatic Browser Fallback & --browser Flag:
   * Original Spec: Relied solely on native desktop window (`pywebview`).
   * What was Changed: Added an automatic fallback to the default browser (Safari, 
     Chrome, Edge) if system desktop webview libraries are missing or restricted.
   * Why: Prevents crashes during evaluation if an examiner's computer has an older 
     OS or strict corporate/university application restrictions.

2. 1-Click Launchers (Run_IDS_Mac.command & Run_IDS_Windows.bat):
   * Original Spec: Required manual terminal commands (`python -m app.launcher`).
   * What was Changed: Created double-clickable scripts in the root directory that 
     auto-check Python, build an isolated virtual environment, install packages, 
     and launch the app in 1 click.
   * Why: Non-technical evaluators and professors can run the project without 
     touching the command line or cloning via terminal.

3. Standalone Pre-Packaged Releases (Zero Python Required):
   * Original Spec: PyInstaller specs were included in packaging folder.
   * What was Changed: Configured a full GitHub Actions CI pipeline that automatically 
     compiles standalone executables (`.exe` for Windows, `.app` for macOS) and attaches 
     them to official GitHub Releases (v1.0.0).
   * Why: Anyone can download a single .zip file and double-click the .exe directly.

4. Non-Destructive Model Adaptation Sandbox vs. Blind Self-Training:
   * Original Spec: Called for model adaptation when concept drift occurs.
   * What was Changed: Implemented a human-audited candidate evaluation registry with 
     an instant, 1-click atomic rollback button, rather than unverified auto-retraining.
   * Why (Crucial Academic Defense): Blind self-training on live network traffic is a 
     major security flaw (adversaries can poison the model by intentionally injecting 
     malicious traffic). Gated candidate testing ensures safety.

5. Database Isolation & Zero Test Leakage:
   * Original Spec: SQLite WAL mode persistence.
   * What was Changed: Cleaned all test fixtures and added automated teardown fixtures.
   * Why: Guarantees the dashboard always starts with 0 events and clean metrics 
     instead of leftover unit-test records.

5. TOP 5 TOUGH VIVA / EXAMINER QUESTIONS & WINNING ANSWERS
--------------------------------------------------------------------------------

Q1: "Why did you use Random Forest instead of Deep Learning (LSTM / CNN) or an LLM?"
Answer: "Deep learning models require significant compute resources, exhibit high 
inference latency (several seconds for LLMs), and act as black boxes. In high-speed 
network security, flows must be classified in sub-milliseconds. Random Forest provides 
deterministic, high-throughput tabular classification, resists overfitting through 
bagging, and integrates natively with TreeSHAP for exact polynomial-time explainability."

Q2: "Does the model simply memorize IP addresses and port numbers?"
Answer: "No. IP addresses and timestamps are strictly excluded from the feature vector. 
The model is trained solely on 28 behavioral flow statistics (packet timing, byte length 
distributions, TCP flag counts). An attacker changing their IP address or port will still 
be detected because their behavioral traffic profile remains anomalous."

Q3: "How does your Explainable AI (XAI) work?"
Answer: "We implement TreeSHAP, an algorithm based on cooperative game theory (Shapley 
values). It computes the exact marginal contribution of each of the 28 features toward 
the final prediction score relative to the baseline expectation, visualizing both 
positive (attack-driving) and negative (benign-driving) feature forces."

Q4: "Why not let the model automatically retrain itself on live traffic?"
Answer: "Blind automated self-training on live network data introduces a severe 
vulnerability known as Adversarial Concept Drift or Model Poisoning. An attacker 
could gradually flood the network with malicious traffic to trick the model into 
accepting attacks as normal. Therefore, our architecture requires candidate evaluation 
and audited human approval with instant rollback."

Q5: "How do you protect privacy and sensitive data?"
Answer: "The system is 100% local. It binds exclusively to loopback 127.0.0.1. Raw packet 
payloads are never stored or transmitted. Only non-reversible statistical flow summaries 
are computed and stored in a local SQLite database."
